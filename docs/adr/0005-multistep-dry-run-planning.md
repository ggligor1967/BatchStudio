# ADR-0005: Typed intermediate planning with staged validation

## Status

Accepted by the maintainer for PRODUCT-D1-I1 (issue #40). Implementation is
admitted on the dedicated work branch. Acceptance does not authorize merge,
auto-merge, tags, releases, package publication or unrelated work.

## Context

At `618547d437df092c11654c4578e540218ff018e4`, the per-file worker passes a
planned output `Path` to the next physical-file validator. PNG conversion to
JPEG followed by rename therefore fails at `is_file()`. The regression
`test_multistep_dry_run_never_creates_intermediates` intentionally expected this
failure while prohibiting intermediate creation. CSV chains similarly fail
when a later `pd.read_csv` sees a non-materialized output.

Source contracts are in [processor](../../core/processor.py),
[operation bases](../../core/operations/base.py), [registry](../../core/operations/registry.py),
[security](../../core/security.py) and the registered operation modules.
[ADR-0002](0002-aggregate-operations.md) and
[ADR-0003](0003-safe-output-boundary.md) remain authoritative boundaries.

## Decision

Use typed symbolic intermediates with staged validation for all nine registered
per-file operations. Preserve physical source checks and propagate only facts
justified by explicit semantics. Conditions requiring future bytes or mutable
execution state are deferred, never silently checked. Normal execution always
performs its own validation and ownership checks.

### Immutable invocation and mutable session

`PlanningContext` captures an immutable run ID, timestamp formatted as
`%Y%m%d_%H%M%S`, ordered input occurrences, configuration/workflow snapshot,
naming pattern and canonical destination root. Nested configuration cannot be
mutated through this snapshot; obtaining a workflow returns a fresh value.
The existing JSON-serializable workflow control format is retained without a
persisted schema migration. UI capture occurs before the worker starts.

`PlanningSession` owns mutable allocator reservations and accumulated read-only
observations. Every invocation gets fresh session state. Reusing a processor
must neither reuse reservations nor mutate earlier statistics, contexts or
results. Observation tokens are not content hashes or atomic filesystem snapshots.

### Artifact descriptors

A descriptor contains original input identity (one-based occurrence and
canonical original path), producing original workflow step index/operation ID,
logical type/format, proposed suffix/destination, known metadata with provenance,
explicit unknown properties and materialization state.

States are `MATERIALIZED_SOURCE` and `PLANNED`. Source filesystem identity,
size and mtime may be observed; no output is promoted to materialized during
planning. A descriptor has no filesystem existence interface. Physical validators
receive only the actual source. Pure naming code may inspect lexical names.

Facts use `OBSERVED_SOURCE`, `CONFIGURATION_INTENT` or `DERIVED_CONTRACT` provenance.
Derived facts retain dependencies on the input evidence and successful producer
semantics. Requested dimensions, format and encoding are intentions, not observed
output. Unknowns include generated bytes, size and parseability, plus relevant
image dimensions/modes, PDF structure, CSV values/dtypes/counts or OCR text.

Never fake `exists`/`is_file`, create placeholders, substitute the original for a
transformed intermediate and call validation equivalent, or read an unrelated
file at a planned destination as intermediate content.

`accepted_types={"any"}` waives only a nominal type restriction. It does not
waive content/configuration/capability checks; batch OCR still needs a concrete
PDF/image branch. `output_type="same"` preserves the logical type, not arbitrary
content facts. Rename has a separate byte-copy preservation rule. An output of
`any` means `UNKNOWN` unless its planner establishes a concrete type. A later
known incompatible type fails; an unknown concrete requirement is deferred.
Initial extension classification does not establish content validity.

### Validation and uncertainty

Stages distinguish structure/configuration/type, actual source, derived metadata,
generated content, capability observation and execution-only environment checks.
Preserve `Workflow.validate`, enabled operation identity/configuration checks,
declared transitions and aggregate restrictions. Disabled operations do not
participate, allocate names or change type; invalid serialized step shape is still
invalid even when disabled. All-disabled workflows remain invalid.

Real sources retain existing traversal/existence/file/extension/500 MiB checks,
a bounded binary read attempt, and the operation's existing physical validator.
The read is not exhaustive integrity verification; Pillow `Image.open` is not
proof that every pixel can be decoded. Readable opaque rename inputs need no
format-aware parse. Schema success means the existing configuration contract
passed; this unit does not redesign generic numeric ranges or library validation.

Each diagnostic includes original step index, operation ID, stable check ID,
stage, outcome, reason and evidence/upstream dependencies:

| Outcome | Meaning |
|---|---|
| `CHECKED` | This specific condition was established. |
| `FAILED` | An actual failure or contradiction was demonstrated. |
| `DEFERRED` | Execution or generated-content evidence is required. |
| `UNSUPPORTED` | The required planning capability is absent. |
| `BLOCKED` | Failed/unsupported/unassessed prerequisites prevent this assessment. |

Disabled steps have a separate disposition. Independent static errors are
reported even when content assessment cannot proceed. A failed/unsupported
producer yields no usable descriptor; downstream input checks are blocked.
A deferred producer may yield a descriptor, with producer-success dependencies
on all derived facts. Known metadata contradictions reject a chain; missing
metadata is deferred, while a missing planner is unsupported.

File verdict precedence is `REJECTED`, `UNSUPPORTED`, `UNASSESSED`,
`CONDITIONAL`, then `CHECKED`. Any failed check rejects, otherwise unsupported
capability refuses, otherwise unfinished assessment is unassessed, otherwise
any deferred condition makes the complete assessment conditional. Since output
production and ownership remain execution-only, otherwise valid shipped plans
are conditional. Individual conditions can still be checked.

### Operation dispositions

All rows include common source/path/configuration checks. Planned support is
symbolic assessment, never physical validation of a future path.

| Operation | Real-input checks | Planned-input support | Propagated facts | Deferred checks | Rejection conditions |
|---|---|---|---|---|---|
| `file_rename` | Existing `is_file`, bounded readability | Any logical type | Type/suffix and existing facts under byte-copy rule | Materialization, copy/copystat, ownership | Invalid config/path or failed producer |
| `image_resize` | Existing `Image.open` | Image | Image type/suffix; requested dimensions/aspect as intent | Actual dimensions/mode, resize/encoding/generated validity | Schema/type/source failure |
| `image_convert` | Existing `Image.open` | Image | Image, intended format/suffix | Conversion, modes/encoder, generated validity | Invalid format/schema/type/source |
| `image_filter` | Existing `Image.open` | Image | Image/suffix, requested filter | Pixels/mode, filtering/enhancement/encoding | Invalid choice/schema/type/source |
| `csv_filter` | Existing parser, column membership, predicate/count evaluation | CSV | Justified preserved column names; observed real-source counts | Intermediate parser/dtypes/values/predicate/count, serialization | Known missing column, schema/source/comparison failure |
| `pdf_watermark` | Existing `PdfReader` | PDF | PDF and suffix | Generated structure, unestablished geometry, overlay/merge/serialization | Schema/type/source failure |
| `ocr_image` | Image validator, live image readiness | Image | Intended text, `.txt`, UTF-8 | Generated image validity, recognition/text/count/accuracy | Unavailable unconditional image/language capability or schema/type/source failure |
| `ocr_pdf` | PDF validator, unconditional mode readiness | PDF | Intended text, `.txt`, UTF-8 | Extraction, OCR, auto fallback need/readiness, text | Unavailable unconditional mode capability or schema/type/source failure |
| `ocr_batch` | Concrete PDF/image delegate | Known PDF/image; unknown branch deferred | Delegate text intentions | Delegate checks and unresolved branch | Known non-PDF/image, invalid delegated config or unavailable required capability |
| `pdf_merge` | Original paths/types and existing PDF consumption validation | No symbolic intermediates; standalone adapter only | Common planned `.pdf` after successful dry finalization | Physical merge/generated validity/ownership | Composition, empty aggregate, wrong/mixed types, existing consume/finalize errors |

Do not synthesize dimensions, PDF structure, schema, OCR text or transformation
success. The minimal planners do not propagate image dimensions or PDF geometry
through transformations.

CSV real-source evaluation retains exact original/filtered counts, including
zero matches, through the same predicate logic as execution. No DataFrame or row
values are propagated as virtual intermediate contents. Only unique simple
parsed header names with an established row-filter/header serialization rule
propagate. Non-string/empty/ambiguous `Unnamed:` headers, outer whitespace and
CSV quoting/separator/newline edge cases remain unknown rather than assuming a
round trip. A known missing downstream column rejects. Membership in a known
schema does not prove value/dtype compatibility. Planned numeric operands are
checked where independent of content; actual intermediate comparisons and counts
are deferred. No source file is substituted for a generated CSV.

`supports_dry_run` retains its meaning. Independent `supports_planning=False`
and a default unsupported planner require explicit opt-in for the nine shipped
per-file operations. Processor planning requires both flags and never falls back
to `execute`/`_execute`. Direct legacy `Operation.execute(..., dry_run=True)`
retains its API and planned `OperationResult.output_path`; that field is not proof
of materialization. Aggregate retains its separate dry-run lifecycle/gate.

### Naming, collisions and revalidation

Planning runs sequentially off Tk in captured input order and enabled-step order.
Normal per-file execution retains the thread pool: this is a dry-run-only exception
to [ADR-0001](0001-threadpool-execution.md), not a new scheduler.

For every step, the run pattern uses the original source stem and current suffix.
Conversion chooses `.png`, `.jpeg`, `.webp`, `.bmp` or `.tiff`; OCR chooses `.txt`;
merge enforces `.pdf`; resize/filter/watermark/CSV/rename retain the suffix.
Rename's `{original}` uses the immediately preceding allocated artifact stem,
so consecutive renames compose. A later non-rename still uses the run-level
original-source naming rule. Counters are original one-based input occurrences,
padded to at least three digits; failures do not renumber later inputs. All plan
timestamp substitutions use the captured timestamp.

Resolve operation naming before containment/allocation. Reuse sanitization,
canonical path equality and `_001`, `_002` collision suffixes, including naming
aliases and host case semantics. Keep intermediate allocations for the entire
invocation even after downstream failure. Reservations/observations are mutable
session state, not part of the immutable snapshot or on-disk ownership.

Occupied ordinary candidates allocate alternatives. Unsafe final/dangling
symlinks and resolved escapes fail rather than being followed. Traversal-shaped
patterns retain existing sanitization; forbidden input traversal and output
escapes remain rejected. Missing output directories require an existing directory
ancestor; a file at the directory/ancestor location fails. Creation/writability
remain deferred, without probing.

Names are deterministic only for a fixed context, order, assessment outcomes and
filesystem observations. Independent plans may propose the same path. Do not
promise identical normal-run paths across changed filesystem state, timestamp,
input order or worker scheduling. Normal runs independently revalidate mutable
inputs/configurations/capabilities, destinations, directory/probe requirements
and exclusive ownership. Earlier planning never bypasses them. Preserve
collision-at-open refusal and identity-aware execution cleanup.

### Side-effect and OCR boundaries

Zero BatchStudio-controlled execution/report filesystem writes: no directories,
probes, temporary processing files, placeholders, outputs, copy/rename, cleanup,
aggregate output or automatic/manual/direct HTML/CSV reports. Do not recognize,
rasterize, transform images/PDFs, render output in memory or invoke output-producing
subprocesses to satisfy a planner. CSV predicate evaluation on a real source is
the retained read-only content check, not a virtual transformed dataset.

Existing read-only readiness probes are permitted separately: fresh Tesseract
version/language checks and bounded Poppler `-v` checks. They do not establish OCR
success. Native PDF planning checks native capability but does not extract text.
Explicit OCR requires the full unconditional stack but does not recognize or
rasterize. Auto checks native capability and explicitly defers fallback need and
readiness; it never extracts native text to decide fallback. Batch follows the
concrete logical branch. No accuracy/text/word count prediction or renewed real-OCR
qualification belongs to this unit.

OS-managed metadata and unrelated settings persistence outside processing remain
exclusions. This is not filesystem sandboxing, an ACL guarantee or an atomic
snapshot. TXT/JSON/XML/XLS/XLSX product admission remains unchanged.

### Results, lifecycle and UI compatibility

`PlanResult` records source occurrence, `COMPLETE`/`PARTIAL`/`NOT_STARTED`
assessment state, verdict, ordered step diagnostics/descriptors, disabled steps
and a final `planned_output` only for a complete nonrejected chain. Earlier
partial step destinations may remain visible as diagnostics.

Execution lifecycle is independently `RUNNING`, `COMPLETED`, `CANCELLED` or
`INCOMPLETE`. A completed assessment may reject a plan. Stop is cooperative between
inputs/steps; an in-progress parser/read is not forcibly terminated. Retain its
evidence on return and mark remaining assessment partial/unstarted. Unexpected
assessment exceptions produce explicit diagnostics and incomplete lifecycle,
never a successful final plan or an all-inputs-checked message.

| Field | Processor dry-run contract |
|---|---|
| `success` | Complete checked/conditional assessment only; successful planning, not transformation |
| `success_scope`, `planning_verdict` | Mandatory planning discriminator and explicit uncertainty; never interpret the boolean alone |
| `output` | Empty in dry-run results and statistics |
| `planned_output` | Proposed final destination only; not generated/owned |
| `processed_files` | Complete checked/conditional per-file assessments; existing aggregate consumed-input count retained |
| `failed_files` | Rejected/unsupported per-file assessments plus existing batch/lifecycle error increments; deferred checks do not increment |
| `skipped_files` | Per-file inputs without complete assessment due to interruption/cancellation/global blocking |
| `results` | Compatibility accepted-assessment records, empty output and explicit nested plan |
| `plan_results` | All input assessments, including rejected/unsupported/partial/unstarted |
| `planning_summary` | Disjoint checked/conditional/rejected/unsupported/unassessed input counts plus separate batch errors |
| `dry_run`/`to_dict()` | Preserve read-only invocation identity; serialize planning fields additively |

Legacy counts are not universally a partition: batch/lifecycle errors may add to
`failed_files`. The new summary provides the per-input partition. Overall verdict
prioritizes failed checks/batch errors, unsupported work, unassessed inputs, then
conditional inputs. Empty valid per-file input is `EMPTY`, not transformation
success; empty aggregate retains its existing one batch-level error.

The UI assessed count includes all complete assessments, including rejected and
unsupported plans; it excludes partial/unstarted plans. It is distinct from the
legacy accepted-plan/aggregate-consumption counter.

Run/Logs show conditional/rejected/unsupported/not-fully-assessed plans, assessed
counts and deferred reasons. Never label them successfully transformed, show an
execution success rate or celebrate. Planned paths do not enter the generated-file
map or trigger file/folder-opening fallbacks. Reports remain refused through every
route and cannot open stale HTML. Checkbox changes or processor reuse cannot
change old run identity. No new export, UI redesign or workflow migration.

Compatibility impact is explicit: processor callers using dry-run `output` must
use `planned_output`; boolean-only consumers must inspect the discriminator and
verdict. Normal execution/result semantics remain unchanged.

### Aggregate boundary

Preserve standalone aggregate-only compilation, original input ordering, wrong/
mixed-type whole-batch rejection, correctly typed partial-invalid-PDF policy,
consume counts and stop/finalization boundaries. No enabled transformations before
or after merge, multiple aggregates, symbolic aggregate consumption or implicit
conversion. Only successful dry finalization publishes a common planned output;
stop/failure never advertises a completed common artifact. The adapter supplies
planning evidence without changing legacy lifecycle counters.

## Alternatives and consequences

Retaining the limitation preserves current validation but does not solve the
multi-step case. Structural-only planning is smaller but loses requested
content-sensitive fidelity and invites misleading acceptance. Materializing
outputs or running transformations violates the write-free boundary.

The selected contract adds bounded operation planners, immutable descriptors,
mutable session allocation and truthful consumer mapping. Shared naming and CSV
predicate logic limit drift. It deliberately declines to simulate generated data.
No virtual filesystem, plugin framework, DAG scheduler or new dependency is added.
The roadmap is the canonical execution-scope record; this ADR owns semantics and
the single acceptance matrix below, not a competing backlog or agent transcript.

## Acceptance criteria

This is the sole canonical AC-01–AC-15 specification. All planning cases require
W0: zero execution/report write attempts, unchanged source/output/temp/report
state, no recognition/rasterization/real transformations. Test setup completes
before interception. Normal phases explicitly permit only existing owned writes.
P/F/S denotes legacy processed/failed/skipped counts, subject to batch-error rules.
The concrete implementations are in [planning tests](../../tests/test_planning_contracts.py)
and the linked existing regressions.

## Verification and stopping conditions

Use [Testing](../TESTING.md) focused/full local commands and required final-head CI.
The old multi-step failure assertion must change explicitly; its no-write evidence
must not be removed or weakened. Report actual exit codes, final head and synthetic
CI integration identity separately. Prior-head green checks are not final evidence.

Stop for a necessary contract change, a required planning write/transformation,
unjustified metadata, an unresolved consumer ambiguity, aggregate/format expansion
or a new dependency. Do not bypass validators or relax ownership to obtain PASS.
